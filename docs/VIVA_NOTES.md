# VIVA NOTES

## How to explain the ER diagram (30 seconds)
"PayOps follows money. A **Merchant** gets a **Payment**, routed by a **SwitchDatabase**. Each state change is a **PaymentEvent** (audit). Each financial payment makes a **JournalEntry** with balanced **Postings** on ledger **Accounts**. The bank sends a **SettlementFile** of **SettlementRecords**; a **ReconciliationRun** compares them with Payments and stores **ReconciliationResults**. **Users** with **Roles** operate it. I own Posting, SettlementFile, SettlementRecord."

## 20 likely questions
1. **Why app_user, not user?** `user` is a reserved word in PostgreSQL; using it needs quotes everywhere. `app_user` avoids that. Java class stays `User`.
2. **Why Long IDENTITY ids?** Small, fast, auto-generated by the DB, no collisions; UUIDs are bigger and slower to index and not needed for an internal tool.
3. **Why NUMERIC(19,4) / BigDecimal for money?** float/double give rounding errors (0.1+0.2). NUMERIC is exact; 4 decimals allow fees/FX precision; 19 digits fit large totals.
4. **What is double-entry?** Every transaction is recorded twice with equal debits and credits, so the books always balance and errors are detectable. Capture: Dr Acquirer Receivable, Cr Merchant Payable.
5. **How do you enforce balance?** Controller sums debits/credits in one `@Transactional` before saving; view `v_unbalanced_journal` audits it. A DB constraint trigger is a possible upgrade.
6. **Why no service layer?** The guide's convention: logic in controllers keeps the project small and easy to follow. Cost: fatter controllers and less reuse; mitigate with private helper methods.
7. **Why entities as JSON bodies?** Same convention (no DTOs). Risks handled: unidirectional relations (no loops), `passwordHash` WRITE_ONLY, lazy-proxy fields ignored.
8. **Is the schema normalized?** Yes, 3NF: each fact once (merchant name only in merchant; payment holds merchant_id). Controlled denormalization: `settlement_record.payment_reference` text is kept because bank files may reference payments we don't have (needed for MISSING_IN_PAYMENTS).
9. **Why both payment_reference and payment_id on SettlementRecord?** Reference = what the bank wrote (always present); payment_id = our verified link (optional, set after reconciliation).
10. **Why a join table user_role?** User–Role is many-to-many; a join table with composite PK prevents duplicates.
11. **Cascade/delete rules?** Money tables RESTRICT (never lose financial history). SettlementRecord → CASCADE from file; ReconciliationResult → CASCADE from run (derived data). Optional links SET NULL. user_role CASCADE.
12. **Why PaymentEvent is separate from Payment.status?** Status = current state; events = full history for audit and dispute handling. Append-only.
13. **Which indexes and why?** Unique: codes, references, file name, username. Foreign keys (joins). payment(status), (created_at), (status,created_at) for dashboards; settlement_record(payment_reference) for matching; payment_event(payment_id, occurred_at); reconciliation_result(result_type).
14. **Why CHECK constraints when Java validates?** DB is the last line of defence against bad data from any source (scripts, other apps).
15. **Why enums as STRING not ORDINAL?** Reordering enum values would silently corrupt ORDINAL data; strings are readable in SQL.
16. **createdBy as String or FK?** String username: survives user deletion, no coupling to teammates' table. Trade-off: no FK integrity (open decision D1).
17. **How is DUPLICATE detected without UNIQUE?** I deliberately did not make (file, payment_reference) unique, otherwise duplicate bank lines could not be stored and reported.
18. **Where are transactions?** `@Transactional` on controller methods that write several tables (capture, refund, settlement posting, reconciliation).
19. **Where does JWT go without a config folder?** Filter + AuthController in controller, JwtUtil in model, security bean in main application class (flagged for approval).
20. **What is SwitchDatabase?** Assumed routing/connection profile of a bank/acquirer/network. It is an assumption, confirmed with team (D2); only that entity changes if wrong.
